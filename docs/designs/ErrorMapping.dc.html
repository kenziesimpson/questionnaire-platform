From a rejected submit to a sentence under a question

The server sends codes keyed by item, never prose and never a value. The renderer turns a code into a message from the question alone, so a failure the browser caught and a failure the server caught read identically.

1 The response body 
{
  "type": "…/problems/submission-invalid",
  "title": "The submission failed validation",
  "status": 422,
  "instance": "/api/run/sessions/01a0951b/submit",
  "items": [
    { "itemId": "itm_02", "code": "answer/required" },
    { "itemId": "itm_03", "code": "date/in-future" }
  ]
}
RFC 9457 problem details, application/problem+json. The items extension is the only part the form reads; it carries an item id and a rule name, and nothing the respondent typed.
2 What the app holds 
const errors: ItemErrors = {
  itm_02: ["answer/required"],
  itm_03: ["date/in-future"],
}

<QuestionnaireForm
  definition={definition}
  answers={answers}
  errors={errors}
  onChange={setAnswer}
  mode="interactive"
/>
One errorsByItemId in packages/ui, used by both apps: group items by itemId, keeping server order. The same shape comes out of the shared validator run in the browser before submit, so there is one error path, not two.
3 What the respondent reads
Which condition?
Answer this question.
When were you diagnosed?
Enter a date that is not in the future.
One catalogue in questionnaire/messages.ts builds each sentence from the question — an item shows its first code, and a message can never carry an answer back onto the screen.
Two codes that never attach to a question answer/not-visible and answer/unknown-item describe the submission, not an item on screen. errorsByItemId drops them, and Wave 3 shows nothing for them — there is no rendered item to hang them on, and the client filters answers to the visible set before submitting, so seeing one means the two evaluations disagreed.
Deliberately empty. What a respondent should see when it happens anyway is gh#23 — a form-level message is the obvious candidate, and it is not drawn here because it is not being built yet.
The admin side is the same shape, with one gap A publish rejection is 422 questionnaire/draft-invalid with the identical items extension, keyed by item and carrying a DraftItemCode. The draft editor groups it the same way and shows it in the publish-checks rail. To build in Wave 3: there is no message catalogue for the ten draft codes yet — questionnaire/messages.ts covers submission codes only. The admin app needs its own, written for an author rather than a respondent, saying what to change and not just what is wrong.
